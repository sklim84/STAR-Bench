# Multi-turn rebuild (WS-E)

`benchmarks_multiturn/` and `benchmarks_multiturn_en/` are generated by this
package. The data files carry no hand edits: running the build reproduces them
byte for byte.

```bash
python -m _experiments.scripts.data_fixes.multiturn.build      # write both files
python -m _experiments.scripts.data_fixes.multiturn.build --check   # build, write nothing
python -m _experiments.scripts.data_fixes.multiturn.verify     # checks and distribution
```

The build needs the platform checkout (`_experiments/scripts/_platform.py` finds
it) and the HOFINET query database, which it opens read-only through the
platform's own connection.

| file | what it holds |
|---|---|
| `spec.py` | the description language: `Scenario`, `Turn`, `Ref`, and the HOFINET fraud-type, §VI, channel and time-slot tables |
| `scenarios.py` | scenarios 1 to 13, plus the helpers the other two files share |
| `scenarios_b.py` | scenarios 14 to 30 |
| `scenarios_c.py` | scenarios 31 to 50 |
| `build.py` | executes each gold call, resolves the references, renders the turn texts, writes both languages and `rebuild_log.json` |
| `verify.py` | the checks, the distribution the paper reports, and the STR narrative coverage |
| `rebuild_log.json` | per scenario: the entities chosen and why; per turn: the gold arguments, the context reference and the result keys |

## Why it is generated rather than edited

The pre-audit file was written by hand. None of its 48 account ids existed in
HOFINET, 82% of its injected tool results shared no key with what the tool of
that turn really returns, and its `predict_fraud` golds used feature
combinations the data does not contain (L3-018, L3-004). A hand-edited fix would
have left the same class of defect one layer down, so the scenarios are now a
spec and the data is its output:

* **Real entities.** Every account, institution, date, amount and channel is one
  that exists in HOFINET and carries the story the scenario tells. A night-bulk
  scenario uses an account the redefined R001 really flags, a smurfing scenario
  an account with hundreds of real counterparties, a `predict_fraud` turn the
  six features of a transaction that is really in the data. `Scenario.why`
  records the reason for each choice.
* **Real tool results.** Each turn's `tool_result` is the output of executing
  that turn's gold call on the platform, so the injected history is what the
  tool layer would have produced.
* **References that resolve.** `Ref(turn, path)` reads a value out of the
  executed result of an earlier turn while the file is being built. The gold
  argument that receives it, the `context_ref` that names it and the figure the
  STR summary quotes are therefore the same value, and the build fails if a
  reference does not resolve.
* **Narratives that cannot drift.** The STR summaries are templates over values
  bound from the turns' own results, so a figure in a summary cannot contradict
  the data. Korean particles, dates and money are rendered by the builder
  (`{acc:은는}`, `{date:date}`, `{amt:,}`), which is what the 4/28 bulk
  substitution got wrong by hand.
* **One pass, two languages.** The English file is written in the same pass from
  the same spec, keyed by scenario id and turn, so it cannot be scrambled the way
  positional matching scrambled it (C1-010).
